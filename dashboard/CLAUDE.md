# dashboard — frontend conventions

React 19 + TypeScript + Vite, Tailwind v4 (CSS-first `@theme` config in `src/index.css` — no `tailwind.config.js`), lucide-react, framer-motion, react-router-dom 7.18.1+ (pinned above the RSC-CSRF advisory range — moot anyway, this is a plain client-rendered SPA, no SSR/RSC in use).

## Design system — non-negotiable, already decided
Premiere Noir now follows [`docs/design/DESIGN.md`](../docs/design/DESIGN.md); its tokens (bone, verdict-*, heat-1..6, state-*, city-1..8) live in the `@theme` block of `src/index.css`. **Retired as AI tells (DESIGN.md section 9):** gradient-clipped title text, glossy gradient/glow gold buttons, the violet corner wash on `body`, and the conic-gradient morphing blob loader. `src/lib/designTokens.test.ts` guards these.
**"Premiere Noir"** (chosen 2026-09-08, evolving 09-07's "Premiere Neon" after direct user feedback that stark white cards on near-black read harsh/basic — the stated reference was the Claude desktop app's warm, layered dark aesthetic). Deliberately not generic SaaS, single committed aesthetic — **no light/dark toggle**:
- **Warm dark, layered surfaces**: canvas → card → well/input each one step lighter, all defined as tokens in `index.css`'s `@theme`. The historical token NAMES were kept through the dark flip so call sites didn't churn: `paper`/`ink` now mean "card surface"/"text on a card" — don't "fix" them back to literal white/black. Anything sitting **on gold** uses `text-on-gold` (`--color-on-gold`), never `text-ink` (ink is light now).
- **Type**: Fraunces serif for the big page titles only (`.font-title`, with `.title-sheen` now just solid text); uppercase JetBrains Mono stays for labels/stamps/KPI values (`.font-display` carries weight/case/tracking); Inter for body. The serif/mono pairing IS the identity — elegant marquee over technical call-sheet.
- **Soft radii** (8–18px via the `--radius-*` token overrides), flat gold CTAs via `.btn-gold` (unlayered CSS — it outranks Tailwind's layered `disabled:` utilities, so its disabled look lives in `.btn-gold:disabled`, not per-usage classes). Only one body wash is allowed: a faint gold house light.
- **Motion**: framer-motion springs on StatTile entrances, per-city `--card-glow` hover shadows on city cards, `.morphing-loader` (a three-bar gold level meter, keyframes in `index.css`) in the page skeletons. Respect `useReducedMotion`/`prefers-reduced-motion` everywhere.
- Per-city categorical accent palette (`src/lib/cityTheme.ts`) **must pass the dataviz skill's `validate_palette.js`** (lightness band, chroma floor, CVD separation via OKLab ΔE, contrast vs. surface) before use — hand-picked hex values have already failed this once. The five neon hexes carried over from Premiere Neon unchanged and still sit on dark surfaces everywhere.
- Shared chat primitives for both assistant panels live in `src/components/ui/ChatBits.tsx` (bubbles, typing indicator, suggestion chips, composer classes) — extend there, don't fork per-panel styles.
- `index.html` is served with `Cache-Control: no-store` (see `server/index.js`) — Chrome was observed reusing per-URL cached copies across deploys despite `no-cache`, pinning different SPA routes to different old builds. Don't relax this.
- `cloud_run/delight_card_renderer` hand-syncs this treatment (canvas glows, filmstrip rail, serif sheen headline, mono labels, gradient meter) in `templates/delight_card.html` plus the accent hexes in `main.py`'s `_ACCENT_BY_CITY` — synced to Premiere Noir 2026-09-08, with all stored cards re-rendered in place. If the dashboard's palette or treatment changes again, update that service's copy too and re-render existing cards (same `brief_id` → same GCS URL) — nothing keeps the two in sync automatically, same discipline as `sdk/` vs `sdk_logic/`.

## Architecture: BFF pattern
`server/index.js` is a thin Express BFF proxying the browser to `tour_data_api` (Cloud Run, requires auth) — **the browser never sees GCP credentials**. `getIdentityToken()` tries the Cloud Run instance metadata server first (production), falls back to `gcloud auth print-identity-token` (local dev, no metadata server reachable — fails fast via a 1s `AbortSignal.timeout`) — same code runs unmodified in both environments. Don't add a separate local-only auth path; extend this fallback chain instead if a new environment needs supporting.

- Dev: `npm run dev` (Vite, :5173) + `npm run server` (BFF, :8787, Vite proxies `/api` to it). To see the real showcase and backtest locally run the server as `RECORDINGS_DIR=../private-data npm run server` (without it `/api/recordings/*` answers 503 and the app shows its "unavailable" states).
- Private recordings: Qloo's developer guide forbids storing Qloo response data in a public repo, so the real showcase and backtest are NOT in git. `server/recordings.js` serves `GET /api/recordings/:name` (`showcase` | `backtest`) from the private GCS bucket `RECORDINGS_BUCKET` (prod, read with the service's own OAuth token) or from `RECORDINGS_DIR` (dev). `src/main.tsx` awaits `loadRecordings()` (4 s cap) before first render; `SHOWCASE` (`showcase.ts`) is a live binding set by `setShowcase`, `getBacktest()` returns null until loaded. Never compute a module-level constant from either: read them in render or a function. Tests and e2e use the committed synthetic recordings in `src/test/fixtures/*.synthetic.json`, regenerated by `node scripts/make-synthetic-recording.mjs ../private-data/<name>.json src/test/fixtures/<name>.synthetic.json --kind showcase|backtest` (synthetic ids start `00000000-`).
- Production: `npm run build` then `npm start` serves the built static files and `/api/*` from one Express process.
- Deploy: run `dashboard/scripts/deploy.sh` (Prateek, never agents). It runs `gcloud run deploy tour-intel-qloo --source=dashboard/ --region=us-central1 --project=liifecalling-academy --service-account=dashboard-sa@liifecalling-academy.iam.gserviceaccount.com --set-build-env-vars=PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 --allow-unauthenticated --set-env-vars=TOUR_DATA_API_URL=https://tour-data-api-602700957663.us-central1.run.app,DELIGHT_RENDERER_URL=https://delight-card-renderer-602700957663.us-central1.run.app,QLOO_GATEWAY_URL=<qloo-gateway URL>,ORCHESTRATOR_JOB_URL=https://run.googleapis.com/v2/projects/liifecalling-academy/locations/us-central1/jobs/tour-campaign-orchestrator:run` and grants `dashboard-sa` `run.invoker` on `qloo-gateway`. The script reads `SERVICE` from the environment (default `tour-intel-qloo`) and refuses any name matching `^tour-dashboard` (the old Google-hackathon submission, never overwrite it). `QLOO_GATEWAY_URL` is `https://qloo-gateway-602700957663.us-central1.run.app`, passed via the `QLOO_GATEWAY_URL` environment variable when running the script (the script refuses while it is unset). Unset env vars make the BFF answer 503, and `/api/campaigns/:id/generate-briefs` answers 503 `orchestrator job not configured`. Public is intentional (the demo UI itself, the required hosted project URL). The Playwright skip-download flag keeps Chromium out of the build.
- Firebase Hosting short link: `dashboard/scripts/deploy_web_app.sh` (Prateek) creates site `tour-intel-qloo` (tolerating only "already exists") and deploys the root `firebase.json`, which 302-redirects every path (`/:path*`) to the Cloud Run address `https://tour-intel-qloo-602700957663.us-central1.run.app`. The root `/` has its own explicit first redirect rule, then the `/:path*` rule. Post-deploy check: `curl -sI https://tour-intel-qloo.web.app/` must show `302` with `Location: https://tour-intel-qloo-602700957663.us-central1.run.app/`. Also check `curl -sI 'https://tour-intel-qloo.web.app/tours/board?sample=1'`: the `Location` header must keep `?sample=1`. This is unverified until the short link is deployed (not live when last checked); if Firebase drops the query string, the judge link must be the run.app URL with the query (`https://tour-intel-qloo-602700957663.us-central1.run.app/tours/board?sample=1`). `web.app` is only a short link: Hosting rewrites to Cloud Run have a hard 60 s timeout and cannot carry the long Tour Board and playbook SSE streams, so the judge path must run on the Cloud Run origin. 302 (not 301) so the target can change without browser caching. The site id lives only in `firebase.json` (`hosting.site`); if it is taken, edit it there (the script reads it). `dashboard/firebase-public/404.html` is never served.

## "Gemini thinking" trace — honest data note
`ThinkingTrace.tsx` is the click-to-expand reasoning panel (matches the Claude/Gemini chat UI pattern). The raw `detectIntent` conversation trace isn't persisted per-brief in BigQuery (the driver only holds it transiently in memory during a run) — `src/lib/deriveTrace.ts` **reconstructs** a factual step sequence from what each brief's real data actually implies (real tool order, real grounding-check notes, the real inserted `brief_id`), framed as "How this brief was generated," never presented as a verbatim captured transcript. If persisting the real trace ever becomes worth it, `orchestration_driver/run_campaign.py`'s `_actions()` output is the real source to capture and store — don't fabricate a more detailed trace than the data actually supports.

## Qloo tour routes
`/tours/board` → `/tours/playbook/:cityId` → `/tours/book`, all deep-linkable with `?sample=1` (or `?sample=long`, see E2E). `src/lib/qloo/playbookStore.ts` is the shared per-(artist, city, sampleSet) playbook cache (Playbook page, Book chapters, Insights cross-domain taste); `BoardState.sampleSet` records which sample set a run used so pages pass it on. Sample playbooks exist for four cities (`fixtures/lumenValePlaybooks.ts`; `samplePlaybookEvents(cityId, { long })` renames Curitiba to "San Juan de los Lagos" for the long set). The Book prints to PDF via the print stylesheet and exports an `.ics` of the chosen stops; "Save as campaign" is live-only (sample tours never reach BigQuery). The BFF answers 503 `tour_data_api not configured` when `TOUR_DATA_API_URL` is unset (no default URL).

Sponsor pitch sheet: `/tours/pitch/:cityId/:brand` (`pages/PitchSheet.tsx`, model and plain-text export in `lib/qloo/pitchSheet.ts`, query carry in `lib/qloo/pitchLinks.ts`). Opened from a "Pitch sheet" link on each Sponsors row (and one per city in the Tour Book, print-hidden). Deterministic and read-only: built only from the finished playbook, the segment store (never loads it), the held workspace snapshot and the recorded/sample week; fixed activation template, no Gemini, no fetch. Display filters apply (non-sponsors and do-not-book names get "This name isn't available for a pitch sheet."). Print CSS is the `.pitch-sheet` block at the end of `index.css`; e2e in `e2e/pitch-sheet.spec.ts`.

## The four-step journey (Plan 7 Task 2b)
The nav is one numbered stepper, the same on desktop (top bar) and phones (bottom bar): Markets `/` → Decide `/tours/board` → Playbook `/tours/playbook/:cityId` → Tour Book `/tours/book` (`components/JourneyStepper.tsx`, targets from `lib/qloo/journey.ts` `journeyLinks`). Playbook leads to the last-opened city (kept in `TourBoardProvider`, keyed by run), else the first held city, else the top-ranked one; with no run every step opens the showcase example. A bare `/tours/board` loads the showcase; `?new=1` shows the brief form ("Try your own artist"). Taste (`/insights`) and the legacy campaign routes stay reachable by URL but are off the nav; `/insights` with no run loads the showcase. Pages are `React.lazy` via `lib/routeImports.ts`; `NextStepLink`/`NextStepButton` preload the next route's chunk when visible (chunk only, never data or a Qloo call) and `index.html` carries prefetch-only `speculationrules` for `/proof` and `/tours/board`. The board reserves height for the tab note, summary line and inline log (a CLS check in `e2e/promoter-path.spec.ts` keeps the total under 0.1). The board leads with `components/qloo/MovesSection.tsx` ("Where fan heat and winnability disagree": the 3 largest fan-heat-rank vs winnability-rank moves, reasons from `lib/qloo/moves.ts`); it is descriptive only, so no copy there may say winnability is better, smarter, outperforms or beats (guarded in `MovesSection.test.tsx`). Its height is fixed so the placeholder and the finished list match.

## Recorded showcase (`?showcase=1`)
`?showcase=1` is a recorded real Qloo run (zero calls). `?sample=1` is the invented Lumen Vale test fixture; use it for tests and layout checks, never as a claim about real data.

See the root `CLAUDE.md` ("`?showcase=1` vs `?sample=1`") for the replay behaviour, wording rules and the record command; `--window` there is the this-week/Book/calendar date window, not trends. Files: `fixtures/showcase.json`, `scripts/record-showcase.mjs`, `src/lib/qloo/showcase.ts`.

## Paste your cities (Plan 7 Task 8)
The brief form has a "Paste your cities" textarea (one per line, "City" or "City, Country"; `lib/qloo/routing.ts` `parsePastedCities` trims, drops blanks, de-duplicates, caps at 8 with "Up to 8 cities — the first 8 will be used."). With cities, `TourBrief.cities` is sent and regions are optional (they only disambiguate names). Rows from a pasted run carry a "Your routing" tag (`candidateSource: "your_routing"`); `routing_unmatched` names show above the list ("Not in our city list: ..."). The recording's optional `routing` key (`{ cities, boardEvents, playbooks }`, `record-showcase.mjs --cities "A, CC; B, CC"`, own `<session>-routing` gateway session) powers Landing's "Try a routing" link (`?showcase=routing`, hidden without it). Every page reads the recording through the `showcase*` accessors, which follow a variant set from the URL (`useShowcaseVariant`, `setShowcaseVariant`); `showcaseQuery` carries the right query between steps. `make-synthetic-recording.mjs` adds a synthetic `routing` section when the source has none.

## Strategist, `?mode=` and WebMCP (Plan 4)
- `src/components/strategist/` holds the panel (`StrategistPanel`), the launcher (`StrategistLauncher`: FAB with `aria-label="Ask the strategist"` opening a full-height `Sheet` dialog of the same name on phones, a top-bar "Strategist" toggle and `StrategistDock` on desktop; only on `/tours/*` and `/insights`; on the Tour Board and Playbook routes the phone FAB is docked inside the sticky action footer (which reserves a right gutter for it, so it never covers scores), on the Book route it is lifted above the footer, guarded by occlusion checks in `layout.spec.ts` and `promoter-path.spec.ts`), the composer with suggestion chips (`SAMPLE_QUESTIONS` in sample mode only; in live mode three board-aware questions from `lib/qloo/strategistSuggestions.ts`, no numbers), and `ToolChips` ("Playbook" for get_city_playbook). State lives in `lib/qloo/strategistReducer.ts` and `useStrategist.ts`; the BFF routes are `/api/qloo/strategist` and `/api/qloo/without-qloo`.
- "Ask about this tour" (Plan 7 Task 7; the launcher, dock, FAB, sheet and toggle are all named so): in the showcase the recording's optional `strategist` key (`[{ question, events }]`, `showcase.ts` `showcaseStrategist` / `recordedQuestion`, questions matched on normalised text) is replayed through `streamStrategist`, and the panel shows the recorded questions as chips plus the line "This example can replay the two recorded questions. Try your own artist to ask anything." instead of a text field (no key means the old composer and note). Every answer, live or replayed, has a collapsible `WorkLog`: Gemini's reasoning summary (labelled "Model reasoning summary", "Gemini's own summary of its reasoning"), one line per call (tool label, status, the gateway's own result summary such as "7 cards"), then the answer with any unsupported numbers flagged; the first replayed answer starts open. Record with `record-showcase.mjs --questions "Q1|Q2"` (each in its own `<session>-ask-<n>` gateway session; context from `strategistContext` in the script, which mirrors `TourBoardProvider.strategistContext`). `make-synthetic-recording.mjs` always rebuilds a synthetic `strategist` section and drops any real one.
- Gateway limits the UI should expect: 4 model rounds and 6 tool calls per turn (then a forced final answer, `stoppedEarly`), so one turn can use up to 5 model calls against the per-session ceiling of 20 Gemini attempts (about four full turns), 12 messages and 1,000 characters per input, and the Gemini ceilings (20 per session, daily cap); the UI shows `CAPPED` and `UNAVAILABLE` as honest errors.
- Sample mode (`?sample=1|long`): `streamStrategist({ sample: true })` replays `fixtures/strategistSample.ts` with no network, for the three `SAMPLE_QUESTIONS`; anything else gets an honest UNAVAILABLE reply pointing at the suggested questions. Without Qloo in sample mode uses a fixed list.
- `?mode=winnability|density|without` on `/tours/board` (default `winnability`, param removed when selected). `without` renders the "Generic ranking" list under the banner "Generic LLM answer — no taste evidence", with no verdicts. Combine with `sample`, e.g. `/tours/board?sample=1&mode=without`.
- WebMCP origin trial: `VITE_WEBMCP_OT_TOKEN` may hold several tokens separated by spaces (commas break `gcloud --set-build-env-vars`); `vite.config.ts` writes one `<meta http-equiv="origin-trial">` per token through `src/lib/originTrial.ts` (tested in `src/test/indexHtml.test.ts`). `scripts/deploy.sh` passes the variable through unchanged.
- WebMCP: `QlooWebMcpTools.tsx` registers six tools when `navigator.modelContext.registerTool` exists: `get_tour_board`, `get_city_playbook` (read-only), `open_city`, `set_comparison_mode`, `build_tour_from_shortlist`, `open_tour_book`. The campaign tools in `WebMcpTools.tsx` are separate.
- MCP for outside agents: see the README ("Connect an MCP client") and `cloud_run/agent_mcp_server/CLAUDE.md`. Private mode is IAM-gated with campaign plus taste tools; public mode (`MCP_PUBLIC=1`) is taste tools only, rate-limited per IP.

## E2E (Playwright)
`npx playwright install chromium` once, then `npm run e2e` (judge path and layout guards at 375 mobile and 1280 desktop). The config starts `npm run dev` with `VITE_QLOO_FIXTURES=1` and reuses an existing server on :5173, so stop any non-fixture dev server first (the judge-path spec asserts the sample banner to catch this). Tests never wait for map tiles. If something else already holds :5173, run with `E2E_PORT=5199 npm run e2e` (and `E2E_PORT=5199 node e2e/snapshots.mjs`). `?sample=long` runs the long-names fixture on the board, playbook and book for layout checks (`&mode=without` adds the Without Qloo state; the layout spec also opens the strategist sheet at 375 and checks 44 px targets inside the dialog); the layout spec covers the playbook and book routes (no horizontal scroll at 360, 44 px touch targets on mobile) and the judge-path spec runs showcase → Guadalajara playbook → Build tour → Book inside the two-minute budget. `node e2e/snapshots.mjs` (dev server up) writes rendered HTML and screenshots into `test-results/` for the taste-skill lint gate; results live in `docs/design/lint-report.md`.
Recording-backed specs (`guided-tour`, `playbook-tabs`, `collab`, `v2-agents`) read the real recording from the server, not the synthetic fixtures, so run them against a built dashboard: `npm run build`; build the gateway (`cd ../cloud_run/qloo_gateway && npm run build`) and start the in-memory collab server `PORT=8094 node dist/collab/devServer.js`; then `COLLAB_FAKE=1 PORT=8098 RECORDINGS_DIR=<dir holding showcase.json> node server/index.js`; then `E2E_BASE_URL=http://localhost:8098 npx playwright test e2e/guided-tour.spec.ts e2e/playbook-tabs.spec.ts e2e/collab.spec.ts e2e/v2-agents.spec.ts` (`E2E_BASE_URL` skips the dev server; stop the two servers yourself afterwards). The same command with `E2E_BASE_URL=https://tour-intel-qloo-602700957663.us-central1.run.app` checks the deployed site. Anything that needs live Qloo, Gemini or web lookups, or writes data on the target site (`live-features.spec.ts`, the note-persistence test in `collab.spec.ts`), is skipped unless `LIVE=1` is set (`e2e/live.ts`); run those only against a deployed site, e.g. `LIVE=1 E2E_BASE_URL=<site> npx playwright test e2e/live-features.spec.ts` (120 s timeout per test). A site with analytics on shows the /v2 taps as a labelled prototype instead of the mock; the v2 spec accepts either.

## Proof and scoring display (Plan 5)
- Proof v3 (Task 4d): the private backtest file may carry a `proofV3` key (written by the gateway's `proofPublishCli`, not by hand). `/proof` leads with it, rendered generically from `proofV3.tests[]` (pre-formatted string tables, claims verbatim, limits, a closed "Per artist/case" disclosure) in the order catch, B, C, A, with the earlier v1/v2 runs below under "Earlier runs". Test C is added as data only. The protocol URL is the `PROTOCOL_URL` constant in `Proof.tsx`. Never write copy saying winnability is better; the claims come from the data. Fixture: `src/test/fixtures/backtest.v3.synthetic.json` (served to e2e).
- `/proof` renders committed JSON only (`src/lib/qloo/fixtures/backtest.json`, `{ runs: [run 1, run 2] }`) and the backtest itself makes no network requests. The one exception is the optional "Live since" section at the top (`LiveStats` in `Proof.tsx`: `GET /api/qloo/stats/trust` and `/team`, derived counts from the gateway's BigQuery analytics; hidden when `enabled:false`, never blocks the page, skipped in sample mode). The /v2 RSVP card uses `/api/qloo/stats/v2` and `POST /api/qloo/v2/tap` the same way (prototype taps, localStorage `tiq.v2.taps`). Never add a live call to the backtest itself, and never write copy that says the playbook beat a baseline: the runs show the generic LLM did better for local acts, and the page says so.
- The "Why this score?" display (floors, thresholds, close-call flag, thin-data reason) comes from the streamed `scoring` event and `city_scored` payload, never from constants copied into the dashboard.
- The Talent card is a hybrid: Gemini proposes local acts, Qloo resolves and ranks them. A row is shown only if its name resolved to a Qloo entity (grounding rule); unresolved suggestions are counted in a muted line, never listed. The source label ("Suggested · in Qloo" / "Popular in city") is text, not colour alone. This is untested on new cases, so no copy may claim it performs better.
- `cloud_run/qloo_gateway/src/scoring/calibration.ts` is generated by `calibrateCli` and never hand-edited.

Sponsors by age group: `/api/qloo/sponsor-segments` (BFF) -> `fetchSponsorSegments` -> `segmentStore` (session cache, loads only on click) -> the sponsors card's "All fans | By age group" control (`cards/SponsorSegments.tsx`). Live runs and the recorded example only (always a live gateway read); the invented sample set has no control. The Tour Book prints only band lists already loaded in the session. Age only, indexes are signed over/under-index values (never percentages), and a US 18-24 band shows the under-21 note.
