# qloo_gateway — conventions
The only service that talks to Qloo. Holds one `qloo mcp` child process (stdio) via `@modelcontextprotocol/sdk`, passing `env: process.env` so `QLOO_API_KEY` reaches it.
- Pure modules (`validate`, `scoring/*`, `geo/*`, `claims/*`, `extract`) have no I/O; test them directly.
- I/O modules take injected dependencies (`McpLike`, `FirestoreLike`, `now()`, `sleep()`); tests pass fakes. Never hit Qloo or GCP from unit tests.
- Cache: L1 in-memory LRU + L2 Firestore `qloo_cache`, TTL on `expireAt` (= createdAt + TTL + 7 d grace). TTL is `QLOO_CACHE_TTL_DAYS` (default 45, invalid values fall back to 45) for every tool except `qloo_trends` (7 days, matching the weekly key), so the cache outlasts the judging window. The board's trends window ends on the Monday of the week (start = that - 90 d), so a cached board costs at most one trends call a week.
- Every Qloo call goes through `resilientCall` (validate → cache → budget → mcp → retry → stale fallback).
- Imports use `.js` suffixes (NodeNext ESM).
- Deploy: container (Dockerfile) to Cloud Run, us-central1, `qloo-gateway-sa`, `--no-allow-unauthenticated`, `--min-instances=1`. `QLOO_API_KEY` from Secret Manager secret `qloo-api-key`.

## Build & deploy
- Local image check (from worktree root): `docker build -t qloo-gateway cloud_run/qloo_gateway && docker run --rm qloo-gateway qloo --version`

The gateway logs the active base URL (never a key) at startup.

## Narrative
One Gemini call per playbook via Vertex REST (ADC token from `google-auth-library`). Claims are verified by `claims/verify.ts`; unverified ones are returned as `removed` with a reason. Besides the declared `entities[]`/`numbers[]`, the displayed `text` is checked: every numeric token (decimals, `%`, thousands separators) must be supported by a declared number, and every declared entity name must appear in the text. Undeclared proper nouns in the text remain uncheckable. Results are cached 7 d under tool `gemini_narrative`. Ceilings: 20 per session (in memory) and `GEMINI_DAILY_CEILING` (default 300) per day, persisted in Firestore doc `gemini_usage/<YYYY-MM>` (with `QLOO_USAGE_BACKEND=firestore`) so restarts and extra instances share it. Budget is reserved per actual Vertex attempt; only a failed Vertex call (non-2xx, network, timeout) falls back to `GEMINI_FALLBACK_MODEL`, never malformed JSON or a schema error. Any failure yields an `unavailable` narrative and never fails the playbook. Models: `GEMINI_MODEL` / `GEMINI_FALLBACK_MODEL`.

## Web (Tavily)
"This week in the city" (`GET /v1/this-week`) uses Tavily `search` only: `search_depth: "basic"`, `max_results` 5, never research/crawl/extract. Hard caps of 25 calls/day and 600/month are checked before every call and persisted in Firestore doc `tavily_usage/<YYYY-MM>` (`QLOO_USAGE_BACKEND=firestore`), so restarts and extra instances cannot exceed them; over cap the route answers `unavailable` (`capped`), never a paid fallback. Every call logs its running count. Results are cached 7 d under tool `tavily_this_week`. `TAVILY_API_KEY` comes from Secret Manager secret `tavily-api-key` (optional; absent means `unavailable`/`no_key`). Summaries are verified by `web/verifyWeb.ts`: items need at least one entity found in the cited source, and numbers in the item text must appear in the cited title/content. All tests use fakes; one manual smoke test only, run by Prateek.

## Strategist
`POST /v1/strategist` (`{ messages, context }` + `x-session-id`) streams SSE from `strategist/run.ts`: a bounded Gemini tool-calling loop. Limits: 4 model rounds and 6 tool calls per turn, then one forced text-only answer (`stoppedEarly: true`). Every Gemini attempt reserves the narrative ceiling (`reserveAttempt`: 20/session + daily). Inputs are re-validated by `strategist/safety.ts` (12 messages, 1,000 chars, 20 context cities); the board context goes to Gemini as data. Client display names (artist, regions, city name/country, and the Without-Qloo inputs) pass `isSafeContextText` (printable, 1-100 chars, no control/bidi characters or `<>`, so "AC/DC" and "P!nk" work); an invalid city or region is dropped, only a malformed shape is a 400. Model-proposed tool args keep the strict `isSafeName`. Tools (`strategist/tools.ts`): the nine allowlisted `qloo_*` insight tools plus `get_city_playbook`, all through `QlooCaller`; unsafe or unknown calls come back as `rejected` and never reach Qloo. Events: `strategist_thinking`, `strategist_tool_call`, `strategist_tool_result` (status incl. `needs_input`, `rejected`), `strategist_message` (`unsupportedNumbers` = numbers in the answer found in no tool result or board score, using the `verifyClaims` matcher via `tokenSupported`), `strategist_error` (`CAPPED`, `UNAVAILABLE`, `ABORTED`, `INTERNAL`), then `done`. An empty model turn is `UNAVAILABLE`, never a blank answer. Without `generate` the route streams `UNAVAILABLE`.

## Without-Qloo
`POST /v1/without-qloo` (`{ artist, regions, cities }` + `x-session-id`) asks Gemini to rank the scored cities with no taste data (`withoutQloo.ts`). Accepted only if the answer is a permutation of the input after `normaliseName`; otherwise `unavailable`/`invalid`. Reserves the narrative ceiling per attempt; only `ok` results are cached (tool `without_qloo`).

## Venues
The place recommend (`venueArgs`, `pipeline/venues.ts`) asks for music venues only: `{target_type:"place", signals:[artist], filter_location: where, include_tags: VENUE_CATEGORY_TAGS, include_tags_operator:"union", limit: 20}` with `live_music_venue`, `concert_hall`, `amphitheater`, `performing_arts_theater` (`urn:tag:category:place:*`, in that order). `night_club` is deliberately not used: it returns strip clubs and `exclude_tags` for adult content had no effect. Qloo still returns places from neighbouring towns and countries, so `sameCityVenues` keeps a place only if `extractEntities`' `geocode` (`properties.geocode.city` / `country_code`) matches the city's ISO-2 country and its accent- and case-insensitive name (or the resolved `locationQuery` city name). No geocode means dropped. At most 10, in Qloo's order, go to `qloo_rank`.
- 0 qualifying venues: no rank call, `venue_fit` absent from the score, the venue card is empty with a partial warning "Qloo lists no music venues in <city> for this artist". 1-2 venues: scored from what exists. Never padded with non-venues. The same-city list also feeds `local_hooks` and the local-moment card. If the rank answers nothing, the card falls back to the same-city venues by affinity (never into the score).
- The venue query differs from the pre-Plan-7 one, so cached boards miss once; calibration was re-derived afterwards (`calibrated-2026-10-24`).

## Major markets
`majorMarkets(regions, cities)` (`pipeline/majorMarkets.ts`) seeds the most populous `cities5000` city of each brief region that is a country (`countryCodeFor`, English names via `Intl.DisplayNames`, plus USA and UK; a state or city region gets none), one per country, in brief order, at most `MAX_MAJOR_MARKETS` (3). It is generic, never per artist. A seed goes through `resolveLocation` like any city (an unplaceable one is `insufficient_data`, still labelled).
- `ScoredCity.candidateSource` is `"heat"` or `"major_market"`. A seed already in the regional heat pool is not duplicated and stays `"heat"` (it is added to the shortlist if the heat pick skipped it, so the board always checks it).
- A seed absent from Qloo's heat list gets `fanHeat = { value: min fan heat among the heat candidates, refs: [] }` and `fanHeatFloor: true` (no Qloo evidence for that number). With no heat candidates at all there is no floor and no seed. Seeds are added on top of the shortlist (8 or `maxStops`), so a board scores up to 11 cities.
- Budget: `sessionBudget.test.ts` covers a cold board with 3 seeds plus 4 playbooks (131 calls in the worst case with every seed needing its second location string, against `SESSION_QLOO_BUDGET` 160).

## Budget
`BudgetGuard` per-session counts roll with the UTC day. The per-session Qloo budget is `SESSION_QLOO_BUDGET` (160, `budget.ts`; a cold board is ~63 calls, or ~87 with 3 major-market seeds; each hybrid playbook adds up to 11). `test/sessionBudget.test.ts` runs a cold board plus 4 playbooks in one session against the real guard. Sessions whose id starts with `mcp-public-` (the public MCP demo) additionally share a daily ceiling `QLOO_PUBLIC_DAILY_CEILING` (default 400, set by `deploy.sh`). Those calls count toward, and are checked before, the global `QLOO_DAILY_CEILING` (2000), so public traffic cannot starve dashboard sessions; over it the tool answers `BUDGET` with "Public demo limit reached for today". The global daily count is persisted in Firestore doc `qloo_usage/<YYYY-MM-DD>` (with `QLOO_USAGE_BACKEND=firestore`, `BudgetGuard.persistDaily`, run after the synchronous `reserve` inside `qlooCall`, bounded to 1.5 s) so restarts and extra instances share it; per-session and public counts stay in memory. A Firestore error or timeout logs (at most once a minute) and falls back to the in-memory count, never failing the Qloo call.

## Location resolution
The harness sends a city only as a fuzzy `signal_location` / `filter_location` / `within` query, so Qloo can place it elsewhere ("Ciudad Juarez, MX" came back as Mexico City, about 1,555 km away; see `docs/qloo/api-notes.md`). `resolveLocation` (`pipeline/tourBoard.ts`, shared by the Tour Board and the City Playbook) therefore runs the in-city `qloo_where_popular {entity, entity_type:"artist", within, limit:20}` first, before the city's other calls, and accepts a query string only if `locationResolved` (`geo/location.ts`) passes: at least `LOCATION_MIN_POINTS` (3) points and a median point-to-city distance of at most `LOCATION_MAX_MEDIAN_KM` (50). Strings come from `locationQueries`, at most `MAX_LOCATION_ATTEMPTS` (3): the original `"<name>, <ISO-2>"` first and byte-identical (the Firestore cache keeps serving good cities at zero cost), then `"<name>, <English country name>"` (`Intl.DisplayNames`). The bare name is never tried and there are no per-city overrides. The first passing string is `where` for every other per-city call and supplies the zones.
- No string passes: the board scores the city `insufficient_data` (never play, hidden_goldmine or de_risk), makes no activation calls, and the `city_scored` city carries `insufficientReason: "location_unresolved"`, `locationAttempts` and a `LOCATION_UNRESOLVED` warning. A resolved city carries `locationQuery` and `locationAttempts`. The playbook answers an `error` event with code `LOCATION_UNRESOLVED` and builds no cards.
- A Qloo error, empty answer or far-away answer (cached or not) is a miss for that string, so the next is tried; no string passing is `location_unresolved`. A city is never scored or given a playbook on an unchecked string.
- Playbook city match (`findCity`, `geo/location.ts`): by `cityId` when the caller sends one (the dashboard passes the board's city id, plus `lat`/`lon`), else accent- and case-insensitive name with the country as ISO-2 or English name (the strategist's `get_city_playbook`). Several same-named cities: nearest the given coordinates, else the most populous. No match is `LOCATION_UNRESOLVED`. The lookup strings use the list's canonical name and ISO-2 country, so the board's cache serves.
- Cost: extra lookups only when a string fails (each is cached). `sessionBudget.test.ts` covers a worst case where every board city needs its second string: a cold board plus 4 playbooks stays well inside `SESSION_QLOO_BUDGET`.
- `zonesFromHeat` stays one row per heat point: those shares are the `fan_concentration` scoring input (calibrated on un-merged shares) and must not be merged. Only the playbook promo-zones card shows `uniqueZones` (rows unique by display name, shares added).

## Scoring calibration and backtest (Plan 5)
- `src/scoring/calibration.ts` is generated by `node dist/scoring/calibrateCli.js --in ../../private-data/calibration/*.json --version calibrated-2026-10-17 --write src/scoring/calibration.ts --report ../../docs/qloo/calibration.md` and is never hand-edited. Inputs are Tour Board recordings only, never backtest cases. The rule is documented at the top of `src/scoring/calibrate.ts`; the numbers are in `docs/qloo/calibration.md`. The 4 recordings the calibration was derived from (Mac DeMarco, Khruangbin, Natalia Lafourcade, Japanese Breakfast) hold Qloo response data and live in `../../private-data/calibration/` (git-ignored; `CALIBRATION_FIXTURES_DIR` overrides). `calibrate.test.ts` re-derives `SCORING` from them and requires an exact match when present (explicit skip otherwise), and always runs the synthetic-recording and default-config `scoreCity` tests. `test/fixtures/live/*.json` are synthetic (generated by `scripts/synthesize-fixture.mjs`); `scripts/check-public-data.sh` (run by `run_tests.sh`) fails if Qloo data is tracked.
- The scoring display (floors, thresholds, thin and close-call flags) is carried by the streamed `scoring` event and each `city_scored` city; the dashboard reads it from the stream.
- The Talent (local acts) card is a hybrid in `pipeline/localActs.ts` and `cityPlaybook.ts`: Gemini proposes up to 10 names, a name that already matches a city-pool artist reuses that entity, and at most `LOCAL_DESCRIBE_CAP` (5) of the others are resolved with `qloo_describe` plus an exact normalised-name match, then ranked with `qloo_rank` (`localActRankArgs`). Grounding rule: a Gemini name is shown only if it resolved to a Qloo entity; unresolved names are dropped and counted (`suggestionsUnresolved`). Without Gemini, the card uses the city-popular artists only; the route also skips the suggestions for `narrative=0` requests and `mcp-public-` sessions (no Gemini, no describes). It is not claimed to beat the generic LLM and has not been tested.
- The backtest (`src/backtest/`) shares request builders with the playbook (`artistTasteArgs`, `cityPopularityArgs`). Unavailable answers are "no answer", not a miss. Backtest results (`backtest/results*.json` originals) are kept private under `private-data/` (Qloo data policy) and served via `/proof`; the CLI writes there by default.
