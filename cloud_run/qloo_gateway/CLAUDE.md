# qloo_gateway — conventions
The only service that talks to Qloo. Holds one `qloo mcp` child process (stdio) via `@modelcontextprotocol/sdk`, passing `env: process.env` so `QLOO_API_KEY` reaches it.
- Pure modules (`validate`, `scoring/*`, `geo/*`, `claims/*`, `extract`) have no I/O; test them directly.
- I/O modules take injected dependencies (`McpLike`, `FirestoreLike`, `now()`, `sleep()`); tests pass fakes. Never hit Qloo or GCP from unit tests.
- Cache: L1 in-memory LRU + L2 Firestore `qloo_cache`, TTL on `expireAt` (= createdAt + TTL + 7 d grace). TTL is `QLOO_CACHE_TTL_DAYS` (default 45, invalid values fall back to 45) for every tool except `qloo_trends` (7 days, matching the weekly key), so the cache outlasts the judging window. The board's trends window ends on the Monday of the week (start = that - 90 d), so a cached board costs at most one trends call a week.
- Every Qloo call goes through `resilientCall` (validate → cache → budget → mcp → retry → stale fallback).
- Imports use `.js` suffixes (NodeNext ESM).
- Deploy: container (Dockerfile) to Cloud Run, us-central1, `qloo-gateway-sa`, `--no-allow-unauthenticated`, `--min-instances=1`. `QLOO_API_KEY` from Secret Manager secret `qloo-api-key`.

## Narrative
One Gemini call per playbook via Vertex REST (ADC token from `google-auth-library`). Claims are verified by `claims/verify.ts`; unverified ones are returned as `removed` with a reason. Besides the declared `entities[]`/`numbers[]`, the displayed `text` is checked: every numeric token (decimals, `%`, thousands separators) must be supported by a declared number, and every declared entity name must appear in the text. Undeclared proper nouns in the text remain uncheckable. Results are cached 7 d under tool `gemini_narrative`. Ceilings: 20 per session (in memory) and `GEMINI_DAILY_CEILING` (default 300) per day, persisted in Firestore doc `gemini_usage/<YYYY-MM>` (with `QLOO_USAGE_BACKEND=firestore`) so restarts and extra instances share it. Budget is reserved per actual Vertex attempt; only a failed Vertex call (non-2xx, network, timeout) falls back to `GEMINI_FALLBACK_MODEL`, never malformed JSON or a schema error. Any failure yields an `unavailable` narrative and never fails the playbook. Models: `GEMINI_MODEL` / `GEMINI_FALLBACK_MODEL`.

## Web (Tavily)
"This week in the city" (`GET /v1/this-week`) uses Tavily `search` only: `search_depth: "basic"`, `max_results` 5, never research/crawl/extract. Hard caps of 25 calls/day and 600/month are checked before every call and persisted in Firestore doc `tavily_usage/<YYYY-MM>` (`QLOO_USAGE_BACKEND=firestore`), so restarts and extra instances cannot exceed them; over cap the route answers `unavailable` (`capped`), never a paid fallback. Every call logs its running count. The query is music- and culture-specific, `live music concerts festivals in <city>, <country> this week`, and results pass only if the title or snippet contains a concert/culture keyword (English, Spanish, Portuguese; whole words, no bare "show"/"art"/"tour", TV/talk/game/reality-show titles rejected; `isMusicOrCulture` in `web/thisWeek.ts`) before Gemini or the citation list sees them. The cache keys carry a query version (`music-v3`), so results fetched with an older query are not served. Results are cached 7 d under tool `tavily_this_week`. `TAVILY_API_KEY` comes from Secret Manager secret `tavily-api-key` (optional; absent means `unavailable`/`no_key`). Summaries are verified by `web/verifyWeb.ts`: items need at least one entity found in the cited source, and numbers in the item text must appear in the cited title/content. All tests use fakes; one manual smoke test only, run by Prateek.

## Sponsor lift
Playbook only; the board's scoring is untouched (`sponsor_fit` stays the raw mean of the top 5 brand affinities, and `activationInputs` makes no baseline call; a test asserts the board activation is identical whatever the baseline says). **Lift is rank based, never an affinity difference:** Qloo rescales `affinity` within each response, so an artist response's affinity and a baseline response's affinity are on different scales (the first implementation showed every sponsor at -2 to -5 "vs city"). The playbook makes three extra `qloo_recommend` calls with no artist signal, `cityPopularityArgs(target, where, 20)` for `brand`, `movie` and `tv_show`, as city baselines (`pipeline/playbookTrust.ts` `rankLifted`). Per item: `artistRank` (1-based in the artist list), `cityRank` (1-based in the city's top 20, `null` when absent) and `rankLift = (cityRank ?? 21) - artistRank` (higher = fans favour it more than the city does). Sponsors are sorted by `rankLift` descending, ties by artist rank; the card has `summary.note` ("Ranked by how much higher this artist's fans rank the brand than the city overall does."), and the merch card `summary.brands` (top 5 by rank lift, also a `merch:brands` narrative evidence item). The local-moment card drops movie and TV titles that are in the city baseline's top 10 (mainstream: the same "High Fidelity" in every city), counts them in `summary.mainstreamDropped`, and sorts the rest by rank lift; place and artist items keep Qloo's order. A baseline that is unavailable (error or empty) means that list keeps Qloo's order with no rank fields, nothing is dropped and there is no note. The baseline refs are cited on the cards that use them.

## Support-act scale
Co-billing and local-acts candidates must have a Qloo `popularity` strictly lower than the headliner's. The headliner's popularity is `artistPopularity` on `runCityPlaybook` (route query `artistPopularity`, 0-1, optional). The board's `resolve` event carries `entity.popularity` (when the board itself described the artist) and the dashboard passes it on. Without it the playbook describes by entity id first, then by name (`qloo_describe`), taking the entity whose id matches. If it still cannot be found, nothing is size-checked: the co-billing and talent cards carry `summary.sizeNote` "Couldn't check act size for this artist." (and that as `emptyCopy` when empty), no counts, and a partial warning "headliner popularity unavailable, support acts not size-checked". Candidates at or above the headliner are dropped and counted (`summary.biggerThanHeadliner`); a candidate with no popularity is dropped and counted (`summary.popularityUnknown`). If nothing remains, the card is empty with a truthful `summary.emptyCopy` (`emptySupportCopy`): "Every Qloo match is bigger than <artist>, so no support pick here." only when every candidate was dropped for size; "No support pick: Qloo had no size data for these acts." when any was dropped for missing popularity; "No support pick: the shared-taste comparison failed for N act(s)." when acts survived the size check but every compare failed. The talent card filters the city pool and the resolved Gemini suggestions before the rank call; the "city mainstream" shared-taste comparison still uses the unfiltered top 5. Shared-taste chips (`sharedTags`, co-billing and talent) keep only `urn:tag:genre:*` tags, chosen from all scored tags before the top-5 cut that feeds the value (`extractSharedTaste().genreTags`, `genreTagNames`); merch chips are genre-only too, never location, keyword or `qloo:*` tags. Promo zones (`displayZones`, display only): a zone named like the city (accent-folded) reads "Central <city>", rows are unique by label with shares added, sorted by share descending; `zonesFromHeat` is still one row per point for scoring. Budget: each playbook adds up to 14 Qloo calls (3 co-bill compares + 1 pool + <=5 describes + 1 rank + 1 compare + 3 baselines), plus one headliner describe once if uncached; the worst `sessionBudget.test.ts` case (87-call board with 3 seeds each needing a second string) plus 4 playbooks is 143 of `SESSION_QLOO_BUDGET` 160.

## Strategist
`POST /v1/strategist` (`{ messages, context }` + `x-session-id`) streams SSE from `strategist/run.ts`: a bounded Gemini tool-calling loop. Limits: 4 model rounds and 6 tool calls per turn, then one forced text-only answer (`stoppedEarly: true`). Every Gemini attempt reserves the narrative ceiling (`reserveAttempt`: 20/session + daily). Inputs are re-validated by `strategist/safety.ts` (12 messages, 1,000 chars, 20 context cities); the board context goes to Gemini as data. Client display names (artist, regions, city name/country, and the Without-Qloo inputs) pass `isSafeContextText` (printable, 1-100 chars, no control/bidi characters or `<>`, so "AC/DC" and "P!nk" work); an invalid city or region is dropped, only a malformed shape is a 400. Model-proposed tool args keep the strict `isSafeName`. Tools (`strategist/tools.ts`): the nine allowlisted `qloo_*` insight tools plus `get_city_playbook`, all through `QlooCaller`; unsafe or unknown calls come back as `rejected` and never reach Qloo. Events: `strategist_thinking`, `strategist_tool_call`, `strategist_tool_result` (status incl. `needs_input`, `rejected`), `strategist_message` (`unsupportedNumbers` = numbers in the answer found in no tool result or board score, using the `verifyClaims` matcher via `tokenSupported`), `strategist_error` (`CAPPED`, `UNAVAILABLE`, `ABORTED`, `INTERNAL`), then `done`. An empty model turn is `UNAVAILABLE`, never a blank answer. Without `generate` the route streams `UNAVAILABLE`.

## Without-Qloo
`POST /v1/without-qloo` (`{ artist, regions, cities }` + `x-session-id`) asks Gemini to rank the scored cities with no taste data (`withoutQloo.ts`). Accepted only if the answer is a permutation of the input after `normaliseName`; otherwise `unavailable`/`invalid`. Reserves the narrative ceiling per attempt; only `ok` results are cached (tool `without_qloo`).

## Venues
The place recommend (`venueArgs`, `pipeline/venues.ts`) asks for music venues only: `{target_type:"place", signals:[artist], filter_location: where, include_tags: VENUE_CATEGORY_TAGS, include_tags_operator:"union", limit: 20}` with `live_music_venue`, `concert_hall`, `amphitheater`, `performing_arts_theater` (`urn:tag:category:place:*`, in that order). `night_club` is deliberately not used: it returns strip clubs and `exclude_tags` for adult content had no effect. Qloo still returns places from neighbouring towns and countries, so `sameCityVenues` keeps a place only if `extractEntities`' `geocode` (`properties.geocode.city` / `country_code`) matches the city's ISO-2 country and its accent- and case-insensitive name (or the resolved `locationQuery` city name), ignoring a trailing "city" word on both sides: Qloo says "New York" where the list says "New York City". This is one generic rule, no per-city lists; it also lets "Kansas" match "Kansas City", accepted because the country code and Qloo's own location filter scope it. No geocode means dropped. At most 10, in Qloo's order, go to `qloo_rank`.
- 0 qualifying venues: no rank call, `venue_fit` absent from the score, the venue card is empty with a partial warning "Qloo lists no music venues in <city> for this artist". 1-2 venues: scored from what exists. Never padded with non-venues. The same-city list also feeds `local_hooks` and the local-moment card, and the places call is cited as evidence there only when a venue survived. If the rank answers nothing, the card falls back to the same-city venues by affinity (never into the score).
- The venue query differs from the pre-Plan-7 one, so cached boards miss once; calibration was re-derived afterwards (`calibrated-2026-10-24`).

## Major markets
`majorMarkets(regions, cities)` (`pipeline/majorMarkets.ts`) seeds the most populous `cities5000` city of each brief region that is a country (`countryCodeFor`, English names via `Intl.DisplayNames`, plus USA and UK; a state or city region gets none), one per country, in brief order, at most `MAX_MAJOR_MARKETS` (3). It is generic, never per artist. A seed goes through `resolveLocation` like any city (an unplaceable one is `insufficient_data`, still labelled).
- `ScoredCity.candidateSource` is `"heat"` or `"major_market"`. A seed already in the regional heat pool is not duplicated and stays `"heat"` (it is added to the shortlist if the heat pick skipped it, so the board always checks it).
- A seed absent from Qloo's heat list gets `fanHeat = { value: min fan heat among the heat candidates, refs: [] }` and `fanHeatFloor: true` (no Qloo evidence for that number). With no heat candidates at all there is no floor and no seed. Seeds are added on top of the shortlist only while the board stays at or under `max(11, shortlist size)` scored cities (so an 8-stop board scores up to 11, a 20-stop board gets no seeds).
- A floored seed has no Qloo fan-heat evidence, so its verdict is capped: `play` and `hidden_goldmine` become `consider`; the other verdicts are unchanged. A seed that is in Qloo's heat pool is a heat candidate with real fan heat and is not capped.
- Budget: `sessionBudget.test.ts` covers a cold board with 3 seeds plus 4 playbooks (143 calls in the worst case with every seed needing its second location string, against `SESSION_QLOO_BUDGET` 160).

## Paste your cities
`POST /v1/tour-board` also accepts `{ artist, cities: [{name, country?}] (1-8, names pass isSafeContextText), regions? (0-6) }`; `maxStops` is optional there. A bad `cities` is a 400 naming `cities`. `resolveRouting` (`pipeline/routing.ts`) resolves each entry with `findCity`: an explicit country (ISO-2, English name, USA/UK) as given; otherwise the brief's country regions in order; with no country region, the name alone only if exactly one city has it. Unmatched or ambiguous names come back as pasted in the first-class event `routing_unmatched { names }` (emitted right after `scoring`, before any city is scored; always emitted in pasted mode, `[]` when all matched). Nothing matched: `routing_unmatched`, then error `ROUTING_EMPTY`, with zero Qloo calls. Pasted mode (`TourBrief.routing`, separate from the back-test-only `extraCities`, which it ignores) scores exactly the matched cities in pasted order: no heat shortlist, no major-market seeds; the heat lookup runs per distinct country of the matched cities (English names, at most 3); each city goes through `resolveLocation` and the usual activation with `candidateSource: "your_routing"`. A city in the regional heat keeps its real fan heat; one absent gets the lowest fan heat of that list (`fanHeatFloor`, no refs) and the floored cap (play and hidden_goldmine become consider); with no heat at all the fan heat is `insufficient_data`. Budget (`test/routing.test.ts`): 8 pasted cities each needing a second location string cost 70 calls on the board, 107 with 4 playbooks in the fake run; the by-construction ceiling is 7 + 8 x 8 + 4 x 14 + 1 = 128 of `SESSION_QLOO_BUDGET` 160.

## Budget
`BudgetGuard` per-session counts roll with the UTC day. The per-session Qloo budget is `SESSION_QLOO_BUDGET` (160, `budget.ts`; a cold board is ~63 calls, or ~87 with 3 major-market seeds; each hybrid playbook adds up to 14, including the three city baselines). `test/sessionBudget.test.ts` runs a cold board plus 4 playbooks in one session against the real guard. Sessions whose id starts with `mcp-public-` (the public MCP demo) additionally share a daily ceiling `QLOO_PUBLIC_DAILY_CEILING` (default 400, set by `deploy.sh`). Those calls count toward, and are checked before, the global `QLOO_DAILY_CEILING` (2000), so public traffic cannot starve dashboard sessions; over it the tool answers `BUDGET` with "Public demo limit reached for today". The global daily count is persisted in Firestore doc `qloo_usage/<YYYY-MM-DD>` (with `QLOO_USAGE_BACKEND=firestore`, `BudgetGuard.persistDaily`, run after the synchronous `reserve` inside `qlooCall`, bounded to 1.5 s) so restarts and extra instances share it; per-session and public counts stay in memory. A Firestore error or timeout logs (at most once a minute) and falls back to the in-memory count, never failing the Qloo call.

## Location resolution
The harness sends a city only as a fuzzy `signal_location` / `filter_location` / `within` query, so Qloo can place it elsewhere ("Ciudad Juarez, MX" came back as Mexico City, about 1,555 km away; see `docs/qloo/api-notes.md`). `resolveLocation` (`pipeline/tourBoard.ts`, shared by the Tour Board and the City Playbook) therefore runs the in-city `qloo_where_popular {entity, entity_type:"artist", within, limit:20}` first, before the city's other calls, and accepts a query string only if `locationResolved` (`geo/location.ts`) passes: at least `LOCATION_MIN_POINTS` (3) points and a median point-to-city distance of at most `LOCATION_MAX_MEDIAN_KM` (50). Strings come from `locationQueries`, at most `MAX_LOCATION_ATTEMPTS` (3): the original `"<name>, <ISO-2>"` first and byte-identical (the Firestore cache keeps serving good cities at zero cost), then `"<name>, <English country name>"` (`Intl.DisplayNames`). The bare name is never tried and there are no per-city overrides. The first passing string is `where` for every other per-city call and supplies the zones.
- No string passes: the board scores the city `insufficient_data` (never play, hidden_goldmine or de_risk), makes no activation calls, and the `city_scored` city carries `insufficientReason: "location_unresolved"`, `locationAttempts` and a `LOCATION_UNRESOLVED` warning. A resolved city carries `locationQuery` and `locationAttempts`. The playbook answers an `error` event with code `LOCATION_UNRESOLVED` and builds no cards.
- A Qloo error, empty answer or far-away answer (cached or not) is a miss for that string, so the next is tried; no string passing is `location_unresolved`. A city is never scored or given a playbook on an unchecked string.
- Playbook city match (`findCity`, `geo/location.ts`): by `cityId` when the caller sends one (the dashboard passes the board's city id, plus `lat`/`lon`), else accent- and case-insensitive name with the country as ISO-2 or English name (the strategist's `get_city_playbook`). Several same-named cities: nearest the given coordinates, else the most populous. No match is `LOCATION_UNRESOLVED`. The lookup strings use the list's canonical name and ISO-2 country, so the board's cache serves.
- Cost: extra lookups only when a string fails (each is cached). `sessionBudget.test.ts` covers a worst case where every board city needs its second string: a cold board plus 4 playbooks stays well inside `SESSION_QLOO_BUDGET`.
- `zonesFromHeat` stays one row per heat point: those shares are the `fan_concentration` scoring input (calibrated on un-merged shares) and must not be merged. Only the playbook promo-zones card shows `displayZones` (rows unique by display name, shares added, "Central <city>" for the city's own name, sorted by share).

## Scoring calibration and backtest (Plan 5)
- `src/scoring/calibration.ts` is generated by `node dist/scoring/calibrateCli.js --in ../../private-data/calibration/*.json --version calibrated-2026-10-17 --write src/scoring/calibration.ts --report ../../docs/qloo/calibration.md` and is never hand-edited. Inputs are Tour Board recordings only, never backtest cases. The rule is documented at the top of `src/scoring/calibrate.ts`; the numbers are in `docs/qloo/calibration.md`. The 4 recordings the calibration was derived from (Mac DeMarco, Khruangbin, Natalia Lafourcade, Japanese Breakfast) hold Qloo response data and live in `../../private-data/calibration/` (git-ignored; `CALIBRATION_FIXTURES_DIR` overrides). `calibrate.test.ts` re-derives `SCORING` from them and requires an exact match when present (explicit skip otherwise), and always runs the synthetic-recording and default-config `scoreCity` tests. `test/fixtures/live/*.json` are synthetic (generated by `scripts/synthesize-fixture.mjs`); `scripts/check-public-data.sh` (run by `run_tests.sh`) fails if Qloo data is tracked.
- The scoring display (floors, thresholds, thin and close-call flags) is carried by the streamed `scoring` event and each `city_scored` city; the dashboard reads it from the stream.
- The Talent (local acts) card is a hybrid in `pipeline/localActs.ts` and `cityPlaybook.ts`: Gemini proposes up to 10 names, a name that already matches a city-pool artist reuses that entity, and at most `LOCAL_DESCRIBE_CAP` (5) of the others are resolved with `qloo_describe` plus an exact normalised-name match, then ranked with `qloo_rank` (`localActRankArgs`). Grounding rule: a Gemini name is shown only if it resolved to a Qloo entity; unresolved names are dropped and counted (`suggestionsUnresolved`). Without Gemini, the card uses the city-popular artists only; the route also skips the suggestions for `narrative=0` requests and `mcp-public-` sessions (no Gemini, no describes). It is not claimed to beat the generic LLM and has not been tested.
- The backtest (`src/backtest/`) shares request builders with the playbook (`artistTasteArgs`, `cityPopularityArgs`). Unavailable answers are "no answer", not a miss. Backtest results (`backtest/results*.json` originals) are kept private under `private-data/` (Qloo data policy) and served via `/proof`; the CLI writes there by default.

## Proof v3 (pre-registered back-test)
Binding protocol: `docs/qloo/proof-v3-protocol.md` (with Amendment 1); ground truth `backtest/city/artists.json` + `cases.json` (public Wikipedia data). Code in `src/backtest/`; every run writes **only** under `private-data/backtest/` (the Qloo data policy; the CLIs refuse any other in-repo path and have no override). One results type, `ProofV3Results` (`schemaVersion: 3`, `proofResults.ts`): protocol commit SHA (last commit of the protocol file), calibration version, Gemini models configured and used, Qloo/Gemini call counts and errors, stop status, one section per test, and `summary` sentences from the pure `summarise` (the claim rule: "X beat Y (p=...)" only if the mean is higher AND the two-sided exact sign test gives p < 0.05, otherwise "Not significant at this sample size: ...", losses named, chance level stated). Build first (`npm run build`), run from `cloud_run/qloo_gateway`; unit tests use fakes only.
- **Test A, city ranking:** `node dist/backtest/cityRankCli.js --batch 1|2 [--out private-data/backtest/proof-v3-city-batch<N>.json] [--dry-run]` (needs `QLOO_GATEWAY_URL`, `gcloud` login). `--dry-run` prints the artists, regions, session ids and expected call budget and builds no client (zero network calls). Per artist the runner runs the live board pipeline in-process with `deps.qloo` = the gateway HTTP caller (`createGatewayCaller`, identity token refreshed every 25 min, a 429 is never retried), session `proof-v3-city-<position>`. **Two passes, one memory:** pass 1 is the plain board; extras are computed from its cities (Amendment 2: played/unplayed-decoy pairs, played in `sha256(artist + city id)` order, decoys from `decoyPool` in `sha256(artist + "decoy" + id)` order, while the list is <= 14 and played <= half; a board with more played than unplayed adds nothing and is flagged); played cities are first re-anchored with the board's own anchoring function (`anchorCity`) and every change is listed; pass 2 re-runs the board with `extraCities` (`TourBrief.extraCities`, scored like heat candidates, `candidateSource: "backtest_extra"`, floored fan heat when absent from the heat list; the live route never reads it, tested). A per-artist in-memory layer (`memoQloo`) serves pass 2's repeated requests, so only the extras cost calls; the board cities of both passes must match or the artist is dropped. One city is scored at a time (`concurrency: 1`) so a stop leaves at most one city's parallel requests in flight. Arms: winnability, fan heat (unscored last, ties by hash order), generic Gemini (temperature 0.2, forced permutation via an enum response schema, one retry, else "no answer" and excluded from that arm), population. Metrics: R-precision, chance level, means, exact sign tests, plus the secondary board-only winnability vs fan heat. The claim rule needs a higher mean, more wins than losses and p < 0.05; `summarise` also emits the protocol's disclosures.
- **Test B, fixed candidates:** `node dist/backtest/fixedRankCli.js [--out private-data/backtest/proof-v3-fixed.json] [--dry-run] [--cases a.json,b.json]` over the 27 reviewed cases (`backtest/cases.json` + `cases-run2.json`): real pick + 9 decoys (lowest `sha256(case id + name)` from the city popularity list; fewer than 9 = "too few candidates", excluded), arms Qloo `rank`, Gemini, popularity order; MRR and sign tests. Session `proof-v3-fixed-<case id>`.
- **Claim-checker catch rate:** `node dist/backtest/catchRateCli.js [private-data/showcase.json] [--out private-data/backtest/proof-v3-catch.json]` (no network). 30 recorded claims, 10 planted false (exactly one token changed: half the number plants use a number real elsewhere in the playbook but not on the cited cards, half a number in no evidence; entity plants swap in a name from another card), catch rate reported per plant type; the false-alarm rate is not a finding (true claims were already accepted by the verifier), all through `verifyClaims` with each playbook's evidence; reports the catch rate and false-alarm rate.
- **Test C, grounding:** `node dist/backtest/groundingCli.js [--showcase private-data/showcase.json] [--out-dir private-data/backtest] [--dry-run]` (needs `QLOO_GATEWAY_URL`, `gcloud` login). Question: do the venues, sponsor brands and local acts exist in the city, Qloo's shipped playbook vs an LLM-only list (Amendment 4). Cities come from the showcase recording's `city_scored` events (both scores, `sha256(city id)` order, <= 10; any difference from the protocol's expected 9 is printed and recorded, the recording wins). Qloo arm: `runCityPlaybook` in-process per city (`deps.qloo` = the monitored gateway caller, session `proof-v3-ground-<city id>`, narrative off, the shipped Gemini local-act suggestions on), venues <= 4 (`venue_fit`), brands <= 4 (`sponsors`), local acts <= 3 (`talent`) in card order. LLM arm: one Gemini call (verbatim prompt, temperature 0.2, schema of three capped string arrays; invalid JSON retried once, then no answer; Amendment 3 retries via `retryingGenerate`). A city whose playbook is LOCATION_UNRESOLVED or errors is excluded from both arms and listed; the Amendment 3 stop rule applies and a stopped run writes only the items file. Outputs, `private-data/backtest/` only (the CLI refuses other paths): `proof-v3-ground-items.json`, `-key.json` (row id to arms, city, category; the reviewer never opens it), `-sheet.html` (self-contained blinded sheet: rows de-duplicated per city, category and `normaliseName`, sorted by `sha256(city + category + name)`, no arm, rank or source anywhere; keys 1-4; answers in localStorage; Download CSV `row_id,rating` with `in_city|other_city|not_exist|cant_tell`) and `-sheet.csv` (empty template). Score: `node dist/backtest/groundingScoreCli.js --csv <downloaded ratings.csv> [--allow-partial]` (no network) writes `proof-v3-ground.json` (`ProofV3Results.grounding`): share "in_city" per arm and category (can't tell outside the denominator, counted apart), per-city shares, the paired two-sided exact sign test and the claim rule; shared rows count for both arms; refuses when more than 5% of the rows are unrated or when the key and items files have different run ids. - **Stop rule (`proofStats.ts` `StopMonitor`, wired by `proofShared.ts`):** stop at once on any 429, a BUDGET error, an error envelope (code, summary, recovery) or thrown error matching rate/quota/limit (the gateway's `RATE` code included), any `stale: true` answer (kept by `createGatewayCaller`), or a Qloo error rate above 10% over the last 20 Qloo calls (evaluated once at least 10 are seen; Gemini outcomes are counted in the call counts, and the first 200 characters of each Gemini error are kept in `geminiErrorTexts`, but they are not in the rate). No request is sent after a stop; requests already in flight may complete. The CLI exits 1 and writes partial results: finished artists/cases are kept, the partly scored one is dropped and listed, the rest are listed as not run. The gateway itself retries a retryable error envelope (RATE included) up to twice upstream before the runner sees it, so a rate limit is noticed after up to 3 upstream attempts. A region whose heat lookup fails or is empty drops the artist (listed); a Gemini call failing with HTTP 404, 429, 5xx or a non-JSON body is retried twice on the same model (2 s, then 6 s; Amendment 3) before the fallback model, and every model failing after its retries stops the run as an infrastructure failure. Running Qloo and Gemini counts are logged after every artist and stored in the results.
