## 1. Endpoint and auth
- Base URL: https://hackathon.api.qloo.com. Header: `X-Api-Key: <key>`. Hackathon keys do NOT work on staging/production; keys die after judging (DG).
- Harness default base is https://api.qloo.com (chunk-ESNY4EJL.js:8). Header `X-Api-Key` matches (chunk-ESNY4EJL.js:500).
- Harness README ("Custom Qloo gateways"): a non-default endpoint needs an exact trust decision before the key is sent. Either `qloo config set base-url https://hackathon.api.qloo.com` (stores URL plus matching trust) or set BOTH env vars to the same URL: `QLOO_BASE_URL=https://hackathon.api.qloo.com` and `QLOO_TRUSTED_BASE_URL=https://hackathon.api.qloo.com`. `qloo doctor` shows the active trust source; `qloo doctor --network` does a bounded live probe (needs key, so run it only deployed). Key itself: `QLOO_API_KEY`.
- ANSWER: yes, the Cloud Run deploy must set QLOO_BASE_URL and QLOO_TRUSTED_BASE_URL (identical, https, no trailing path) plus QLOO_API_KEY. Without them `qloo mcp` talks to api.qloo.com and the hackathon key is rejected (expect QLOO_HTTP_ERROR 401/403, or no key sent). README is silent on whether QLOO_BASE_URL alone is enough; assume not.
- Harness endpoints used: /v2/insights, /v2/analysis/compare, /v2/trending, /v2/tags, /search, /entities. DG forbids legacy /recommendations and /recs.
- DG: invalid parameters are SILENTLY IGNORED (no error). This is the main hazard: a wrong param produces plausible-looking but unscoped data.

## 2. Rate limits, quotas, rules
- DG: monthly quota and rate limits "set for typical hackathon projects"; raisable on request via Discord #api-help. No numbers published. api-overview and DD: silent (confirmed).
- /search reference mentions 429 and caps (take max 199, 100 pages, radius max 100 mi). /v2/tags and /v2/audiences: take max 50, 100 pages. Insights: take default 20, max 50 (DD).
- Caching, bulk use, redistribution: docs silent. Terms: https://www.qloo.com/legal/terms (not read; says API terms ship with client docs). Devpost rules not read here; check mcp devpost get_hackathon_rules before claiming caching is allowed.
- Harness-side caps: limit 1-20 per call, default 10 (QLOO_TOOL_DEFAULT_LIMIT/MAX_RESULTS), arrays bounded to 20 items, strings 2000 chars. Our validate.ts:60 limit 1-20 matches. rank has no limit arg and uses take=options.length.
- Implication: tourBoard fans out 3 + regions + per shortlisted city 7 calls (x8 cities) plus entity resolution calls. Quota is unknown, so measure calls/run first (section 6, call 0).

So signal.location works for artist at least with demographics; whether it moves results when only entity signals are given is undocumented.

### 3b. Location params (DD)
- signal.location = WKT POINT/POLYGON or locality ID; signal.location.query = fuzzy name ("New York City"); .radius (m, max 800000, POINT only); .weight. filter.location = "lat,lon", WKT, or entity UUID; filter.location.query = fuzzy name; .radius (default 10% of locality diameter or 2414 m). WKT is lon-first (R recommendations-for-restaurants-similar-to-a-given-place...).
- Harness maps signal_location -> `signal.location.query` and filter_location -> `filter.location.query` only (qloo-tools.js recommend/rank). It cannot send WKT, lat/lon or entity ids. where_popular `within` -> `filter.location.query` on `filter.type=urn:heatmap`.
- recommend with a signal needs `signal_location` only when a demographic is given; with no signals/tags/location/demographic it returns needs_input, and filter_location does NOT count as a signal (qloo-tools.js ~l.401).

### 3c. Verdicts
1. recommend brand/movie/artist/tv_show with signal_location - G/pipeline/tourBoard.ts:67,69,70,71. VERDICT: RISK/likely MISMATCH. PM lists no location param for these types; only the demographic recipe shows signal.location on artist. Silent-ignore means every city may return the same list, making sponsor_fit/local_hooks identical across cities. Fix if data check A shows no city variance: (a) add `demographic` (e.g. "25-44") with signal_location so the documented recipe shape is hit, and/or (b) for brands use place-based proxy (recommend place with filter_location, then brands via `filter.references_brand`/entity properties) or heatmap affinities; (c) mark such components `insufficient_data` rather than score them.
2. recommend place with filter_location - tourBoard.ts:68. MATCH (place accepts filter.location; query form in DD and R find-italian-restaurants..., recommendations-for-restaurants-similar-to-balthazar). Note R shows affinity is null without a signal entity; we pass signals so fine. Note it is a venue list, not an artist-affinity list; fine for hooks.
3. recommend artist with filter_location only - cityPlaybook.ts:72. MISMATCH (two ways). (i) artist has no filter.location (PM). (ii) harness refuses: no signal -> needs_input. Result: proxies always empty, talent card always "empty", talent overlap never computed. Fix: `{ target_type:"artist", signal_location: where, demographic:"25-44", limit:5 }` (matches the personalize recipe) or `signals:[artistEntityId]` plus signal_location. Also consider R get-trending-artists (trending with filter.type artist, no entity) as "mainstream" proxy.
4. where_popular -> heatmap - tourBoard.ts:72,140. extract.ts:23-35. Request `filter.type=urn:heatmap`, `signal.interests.entities=<id>`, `filter.location.query=<name>` is the documented shape (https://docs.qloo.com/reference/heatmaps-use-case). Response `results.heatmap[].location.{latitude,longitude,geohash}` and `.query.{affinity,affinity_rank,popularity}` (R create-a-heatmap...muji, heatmap-for-brand-jacquemus). VERDICT: MATCH on shape; harness returns the heatmap array as envelope `results` sorted by query.affinity (qloo-tools.js:605), exactly what extractHeatPoints reads. Unverified: whether take=20 caps point count (heatmap of a whole country may be coarse), and whether `filter.location.query=<country or region>` works for big areas (R uses a city or WKT polygon). Optional improvement: add query.affinity_rank (0-1) as a normalised field; extract.ts:31 currently ignores it.
5. compare_audiences overlap - cityPlaybook.ts:10-14,55,57,84,87; dashboard/src/lib/qloo/adapters.ts:68-79. VERDICT: MISMATCH (high confidence). Documented response of /v2/analysis/compare is `results.tags[].{tag_id,name,popularity,query.score}` (R compare-two-brands-audiences); with filter.type it returns entities of that type. There is NO scalar overlap/similarity/score on `results`, and the scale of query.score is undocumented. Harness passes `results` through boundedValue (object with tags array, capped 20). So overlapOf returns NaN always: co_billing items never appear and talent overlap stays null. Also compare takes `a.signal.interests.entities`/`b...` (harness does this correctly). Fix: replace overlapOf with a function over `results.tags[]` (e.g. share of tags with score>0, or weighted mean of normalised query.score), OR compute overlap yourself as Jaccard/weighted overlap of the two artists' `qloo_entity_tags` outputs (data we already fetch, 0-1 by construction). Do not label anything "0-1 overlap" until section 6 call 5 shows the scale. adapters.ts:75-76 hard-rejects values outside 0..1 so a real score >1 is dropped silently.
6. rank - tourBoard.ts:77. Request is insights with `filter.results.entities=<resolved ids>`, signals + signal_location, take=#options (qloo-tools.js:500). Response entities with `query.affinity` (0-1 per R). compactEntity reads entity.affinity ?? query.affinity (qloo-tools.js:~137) so MATCH for affinity. Risks: place options are passed as NAMES and resolved via /search with type place (ambiguous names in other cities will come back needs_input, and tourBoard ignores that: extractEntities on needs_input yields [] so venue_fit is silently empty). Fix: pass the entity_ids already returned by `places` (extractEntities(...).entityId) instead of names (tourBoard.ts:75-77); harness accepts UUIDs. Affinity may be null without a signal entity (R); we send signals so OK. signal_location on place+rank is untested.
7. trends - tourBoard.ts:138,150. Documented: GET /v2/trending, `filter.type`, `filter.start_date`, `filter.end_date`, optional `signal.interests.entities`; response `results.trending[]` = `{date, population_percentile, population_rank, population_rank_velocity, velocity_fold_change, population_percent_delta}` (https://docs.qloo.com/reference/get-trending). Harness returns a different envelope: `series:[{entity, points:[...trending items]}]`, not `results`. VERDICTS: (a) tourBoard.ts:150 `trends.envelope.results ?? null` is MISMATCH: always null. Fix: `trends.envelope.series ?? null`. (b) adapters.ts:20-40 toTrendSeries expects `series[].date/value|popularity|score` or an object with `.series`; real points are under `series[0].points` and the value fields are `population_percentile` (and `velocity_fold_change`, `population_percent_delta`). MISMATCH. Fix: accept `t[0].points`/`t.series[0].points` and add "population_percentile" to the value key list (adapters.ts:25); consider charting velocity_fold_change. (c) 90-day window with start/end YYYY-MM-DD is valid; R trending uses a 7-day window; whether daily points exist for a 90-day span is undocumented (check call 6). Also events.resultCount (tourBoard.ts:54) counts `results` only so trends/series will show 0; harmless.
8. audience_demographics - tourBoard.ts:136,148; adapters.ts:8-18. 9. entity_tags - tourBoard.ts:137, cityPlaybook.ts:71,95. Request `filter.type=urn:tag` + `signal.interests.entities` (R get-the-taste-tags...). ## 4. Entity types (DG, DD)
DG lists on the hackathon server: artist, book, brand, destination, movie, person, place, podcast, tv_show, video_game (note `video_game` here vs `videogame` in DD/harness; harness maps `videogame`). Harness adds search-only types locality, actor, album, author, director. Our validate.ts lacks `destination` and `locality` for recommend. Nothing in the docs says a listed type is absent on the hackathon server; docs silent on whether data volumes differ from production. Verify with call 1.

## 5. Risks
- Coverage outside the US / mid-tier artists: docs silent. Examples are NYC/Chicago/Denver/Paris. Qloo markets "global consumer affinities" (search snippet, qloo.com) with no coverage statement. Expect sparse heatmaps and thin place data for small markets; our `insufficient_data` handling and warnings must stay on.
- Silent-ignore of invalid params (DG) means wrong-param bugs look like valid output; always compare results across two cities.
- Heatmap needs "at least one valid signal" (heatmaps-use-case); an unresolved or obscure artist (no taste data) yields empty/error, not a fallback.
- Compare returns tags, not entities, by default; scale undocumented.
- Quota unknown; fan-out is ~8 shortlist x 7 + overhead per run; BUDGET guard exists (tourBoard.ts:55) but is gateway-side only.
- Keys expire after judging; the deploy must degrade to cached/stale data (stale flag exists).
- Popularity filter (`filter.popularity.min`) exists for artists, so a "mainstream vs niche" split is possible (R surface-popular-restaurants-with-no-user-data), and `describe` popularity (0-1) can classify mid-tier artists.
